# 文档布局：四态分离与工序生命周期

文档腐化的根源通常不是写得差，而是没有结构：现行真相、未来意图、过程记录、历史档案堆在同一层，靠记忆和索引表维持秩序——索引先分叉，然后一切跟着腐化。本规范**既是放置规则**（一份新文档该去哪），**也是识别规则**（一棵既有文档树如何归类）：符合规范的文档树，凭路径与 frontmatter 即可推导每份文档的状态、模块与角色，不依赖任何注册表。

设计的过程本身——业务拆解、模式选择、组件级修改方案的产出——遵循 design-before-coding skill；本规范只决定这些产物的存放位置与生命周期，两份 skill 配合使用。

## 文档根：四态分离

文档根目录（名称项目自定，如 `doc/`）下只允许四个状态目录加一个导航页：

| 目录 | 状态 | 只回答的问题 | 纪律 |
|---|---|---|---|
| `design/` | 现行真相 | 系统现在是什么 | 唯一权威，只写现行内容 |
| `plan/` | 意图 | 接下来做什么 | 只放全局意图，不按模块分 |
| `works/` | 执行 | 正在做什么 | 一级只有工序目录 |
| `history/` | 记忆 | 怎么走到这里的 | 冻结只读 |

- **位置即状态**：文档处于哪一态由路径表达，不靠登记表说明；
- 四态职责与「位置即状态」不可缺，目录名可依项目惯例调整；
- **反占位**：目录与文件在内容诞生时创建，不预留空文件、不预留索引行——plan/ 与 works/ 可以在第一个意图、第一个工序出现时才诞生；
- 导航页 `README.md` 只写阅读顺序与各层各模块入口，不维护逐文件状态表（位置与 frontmatter 已完整表达状态，第三份登记表必然分叉）；
- 本规范自身以 skill 形式存在，不在文档树内；仓库级其他规范（命名、代码目录等）不属文档布局管辖。

## design/：层次 × 模块

一级只放两类内容：

1. **全局文档**（frontmatter `module: global`）：跨模块的现行真相，按层次固定命名——`product.md`（产品层：需求画像、架构总览、组件划分）、`architecture.md`（系统层：进程或服务拓扑、技术基线、跨模块机制）；其他全局主题按小写连字符命名，保持少而精。
2. **模块目录**：`design/<module>/`，一个模块一个目录。**模块清单由目录名推导**——design/ 下有哪些模块目录，模块就有哪些，不另行注册；frontmatter 的 `module` 字段取值即这些目录名（跨模块取 `global`）。

模块目录内部：一份入口规格 `spec.md` 加专项文档（按主题命名），专项文档围绕规格；**场景（业务流程、用例）是规格内部的章节维度，不建目录**——避免场景与模块两个维度交叉。模块目录内部不再嵌套子目录；模块过大时拆模块，不加深目录。

**一处一事**：每类事实只有一个权威文档，其他地方引用不复制；一次决策需要同步修改多份文档里的同一事实，就是违规信号。

## plan/：固定主题

一级只放三个固定主题文档，不建子目录、不按模块分（意图是全局视角，模块级的意图写在工序 brief 里）：

- `roadmap.md`：里程碑与工程量；
- `risks.md`：风险清单与缓解；
- `open-questions.md`：跨工序开放问题。工序立项时从这里领取；被领取的问题标注去向工序ID，关闭时记结论落点，不删除。

## works/：工序工作区

一级只有工序工作区目录，不允许散文件。目录名即工序ID：`YYYY-MM-DD-<短名>`（日期为立项日，归档不改名）——无需中心发号，目录排序即时间线。

工作区内部：

- `brief.md`（立项锚点，必须）：需求、背景、验收标准、领取的开放问题；
- 过程文件（调研笔记、方案迭代、实测记录、评审往返）自由命名，只准放本目录；代码产物归代码目录；
- `result.md`（收口锚点，必须）：验收结果＋**结论落点表**——每条活结论登记落到 design/ 哪个文件哪一节；每条坑登记对策落点或坑档案条目。

生命周期四段：**立项**（建目录写 brief）→ **执行**（过程文件只进本目录）→ **收口**（写 result）→ **归档**（整目录移入 history/works/，frontmatter 的 layer 改为 history、status 改为 frozen，目录名不改）。两条硬规则：**收口是归档的前置条件**——过程文档退役与结论进入现行真相必须同时发生；**归档工序不得作为设计依据**——归档件只是证据，活结论必须蒸馏进 design/ 之后才可被现行文档引用。

## history/：记忆

一级三个去处：

- `decisions/`：整篇决策文档（调研决策链、被取代的方案，frontmatter 标注 `superseded-by`）；轻量单条决策放 `decisions/adr/`，编号式命名（`0001-<短名>.md`，一条一个文件），内容三段：背景、决策、否决的替代方案。
- `works/`：已归档工序，保持原工序目录结构整体移入。
- `pitfalls.md`：坑档案。每条坑三个必填字段：**现象**（观察到什么）、**存续条件**（什么前提下坑仍在；消失的判定与实证日期；预期消失的写明消失条件）、**对策落点**（现行文档中的防御位置）。仍然存在的坑，对策写进 design/、档案存条目；已消失的坑，条目保留（防同类问题复发重踩）并标注实证；无普适价值的过程性意外留在归档工序内，不进档案。

history 冻结只读，唯一例外是坑档案允许更新存续状态（坑消失时补实证）。

## 状态表达：frontmatter

每份文档带 frontmatter（机器可读，支持渐进式探索）：

```yaml
---
layer: design        # design | plan | works | history，必须与所在目录一致
module: storage      # design 层与工序必填：所属模块（global 表示跨模块）
status: current      # draft | review | current | active | closed | frozen
updated: 2026-10-12  # 最近一次实质修订
---
```

- status 合法值随层固定：design 层 draft→review→current；plan 层 draft/current；works 层 active→closed；history 层恒为 frozen。必写不省略，保证可直接检索盘点；
- **一致性规则**：layer 与目录位置矛盾、status 越出本层值域、module 与模块目录不符，发现即修。

## 违规信号

出现任何一条，即有文档放错位置或状态失真，按本规范归位：

- 同一文档的状态在两处登记且互相矛盾；
- 一次决策需要同步修改多份文档里的同一事实；
- 现行文档引用未归档的过程文档作为依据；
- 同一文件里混着事前方案与事后回填，靠内联标注区分版本；
- 文档根一级平铺着现行、历史、占位三类文件，或模块文档散落在 design/ 一级；
- works/ 或 plan/ 里出现不属于该层的内容；
- 坑记录不带存续条件——坑已消失文档仍当它存在，或坑还在文档已沉默。
