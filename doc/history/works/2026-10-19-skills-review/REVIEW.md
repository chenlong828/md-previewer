# arch-design-spec 规格整合与评审备忘

> 状态：已评审并确认（2026-10-21，第 7 节 8 问结论与后续决策见同目录 result.md）。本文记录「原始意图如何被整合成 skill」的裁决、冲突处理与评审过程；skill 正文见 `.agents/skills/arch-design-spec/SKILL.md`。

## 1. 整合目标

原始输入已经给出完整的判据骨架，但仍是「原则清单」，直接做成 skill 会有三个问题：原则之间缺少裁决顺序、部分条目互相张力、没有可裁剪的流程与产物。整合做四件事：

1. 保留原始 5 组判据、3 条良好设计要求、4 个级别的全部意图，不丢条目；
2. 把每条原则变成可执行动作、可检查证据、可裁剪产物；
3. 补上原始清单没有单列、但目标明确要求的「冷热路径」；
4. 让 P 级不只是标签，而是决定流程重量、产物和人工门。

## 3. 关键裁决

### 3.1 分层顺序与依赖倒置

原始表述是「基础设施 → 领域 → 整合」「上层只能调用下层」「依赖倒置」。三者直接拼在一起会打架：如果源码依赖也必须向下，领域层就会依赖 ORM/HTTP；如果依赖倒置成立，基础设施又必须依赖领域定义的端口。

裁决：把「调用图」和「源码依赖图」分开。

- 调用图：L2 整合 → L1 领域契约 → L1 自己的端口；L0 基础设施实现端口，由组合根注入。
- 源码依赖图：L0 → L1 端口（实现），L2 → L1 契约；L1 只依赖自己的端口与值类型；除组合根外不得 import L0 具体类型。
- 这样「调用向下」与「依赖指向稳定」同时成立，领域层不会依赖 ORM/HTTP，基础设施的变化被挡在端口后面。

事件单独处理：事件不是反向调用。发布者只依赖事件契约/端口，不依赖订阅者；订阅者依赖事件契约。领域可以发事件，但不会反向调用整合层。

### 3.2 同层不相认

同层横调禁止，但共享需求必须有出口。裁决为三条下沉/上提通道：

- 共享数据 → 下沉为数据服务（L1 基础子层或 L0 数据适配器），所有写入口集中在它这里；
- 共享编排 → 上提 L2 整合层；
- 共享业务规则 → 抽 L1 领域服务，或确认是同一能力后合并。

数据服务不算「同层兄弟」，而是所有写入口的下沉点；其他模块只通过契约写，不直连存储。需要时把 L1 再分 L1a 领域基础（数据服务、共享领域服务、值对象）与 L1b 领域能力（业务模块），只允许 L1b → L1a。L2 之间共享编排则合并或下沉 L1；L0 通用技术库可同层复用，但不得含业务语义。

### 3.3 扇出与扇入

- 扇出按「直接依赖的下层模块数」计算，同一模块的多个契约按 1 计；同步 + 异步都算；排除标准库、日志/指标/配置等横切工具、纯值类型。否则任何模块都会被日志和指标撑爆。
- 硬上限 8，目标 3–5；热路径上的模块扇出 ≤5，优先 ≤3；整条热路径的同步跨模块调用建议 ≤5，优先 ≤3。热路径的每个同步依赖都是失败点。
- 超限的处理只有三种：按能力拆分、插入有业务价值的聚合模块、把编排上提到 L2。明确禁止「加一个透传聚合层把数字降到 8 以下」。
- 扇入不设上限；1–2 局部、3–5 共享、6+ 平台级。平台级必须契约评审、兼容性测试、废弃策略，改动更谨慎。

### 3.4 业务模块与技术边界模块

原始要求「业务模块必须有业务价值，机械转发没有存在价值」，但防腐层/适配器/仓储天然很薄。裁决为两类模块：

- 业务模块：必须拥有业务能力、规则或数据；用价值测试和删除测试卡住机械转发。
- 技术边界模块：可以薄，但价值是隔离外部模型、稳定契约、封装访问策略；不能冒充业务模块。

删除测试：删掉后复杂度消失 → 透传，合并/删除；复杂度集中或某个保证消失 → 真边界，保留。

### 3.5 业务重叠

「没有交隔」按「没有交叠」理解（若原意不同请指出）。裁决为三张唯一性约束：

- 一个业务能力只有一个 owner；
- 一条业务规则只在一处实现；
- 一份业务数据只有一个写入口。

处理顺序：同能力同变化原因 → 合并；能力混装 → 按能力重切；共享规则 → 抽领域服务；共享流程 → 上提 L2。不允许两个模块都自称 owner。

### 3.6 冷热路径

原始 5 组判据没有单列冷热，但目标是「冷热路径明晰」，因此补为一级章节。裁决：

- 只分热/冷两类；混合路径在契约边界拆成「热同步段 + 冷异步续段」，不内联。
- 热路径：最小同步依赖、禁用冷活内联、专用资源、显式超时/取消/背压/降级、错误可重试分类、缓存有测量与失效。
- 冷路径：幂等消费、去重、退避重试、DLQ、重放、checkpoint、积压/延迟观测、最终一致与最大延迟。
- 冷热不共享线程池/队列/连接池/锁/事务；冷路径可暂停/限流，不能拖垮热路径。
- 不设「温路径」；确有中间态时，明确它按热还是冷的失败/延迟语义处理，不能含糊。

### 3.7 契约

原始定义为「签名 + 不变量 + 错误模式」，保留为核心三件套。热路径/跨进程契约再补运行语义：幂等、顺序、并发、超时/取消/背压、一致性/可见性、版本/废弃。

契约只出现稳定概念；存储 schema、传输协议、第三方 SDK、序列化格式、重试策略、厂商选择都算易变决策，不得进入契约。契约测试是模块验收面；要绕过契约测内部，先改模块形状。

### 3.8 复用与装配

- 继承只在框架强制时使用；其余组合 + 接缝。
- 第二次出现即触发归位；同一语义、同一变化原因则抽到模块库；只是形似则记录不抽取的理由。这里比原文「必须进入模块库」多了一个「同一变化原因」的限定，避免把巧合重复抽成错误抽象。
- 取数/转换/编排只在 L2；调用方拼装一律下沉或上提。
- 依赖选择只在组合根；模块内禁止环境分支选实现；配置在根处类型化并校验。

### 3.9 状态与数据

- context 只放请求级横切事实（租户、用户、截止时间、取消、trace 等），不放业务状态，也不当 service locator。
- 模块级可变业务状态禁止；重启/双跑行为一致；跨实例正确性靠幂等键、乐观并发、唯一约束，不靠本地锁。
- 缓存是派生状态，必须有失效与陈旧度说明；连接池/线程池是基础设施状态，允许存在但必须封装且冷热隔离。
- 共享业务数据一个写入口（数据服务）；读走 owner 契约或登记过的只读投影；禁止多处直连存储。
- 事务边界在 L2 用例；数据服务提供事务性操作；跨模块分布式事务用 outbox/saga，不放大本地事务。

### 3.10 P 级

| 级别 | 核心判据 | 人工门 |
|---|---|---|
| P3 | 单模块局部、无公共契约/schema/依赖/热路径行为变更、自动测试可覆盖 | 自动测试 + 常规评审 |
| P2 | 非核心 schema/内存表字段、实质性跨文件或跨模块、新增内部依赖/适配器、兼容性契约变更、非核心配置、热路径局部优化但不改契约/依赖/资源隔离 | 人最终确认，可异步；设计可由 agent 完成 |
| P1 | 模块切分/合并、新业务模块、核心契约/核心 schema/数据所有权/分层/热路径架构变更、跨团队/高爆炸半径/不可逆、扇出超限或扇入进入平台级 | 人参与切分与契约定义 + 最终确认；设计冻结后才编码 |
| P0 | 业务目标/权属/约束说不清、需求冲突、无可行架构、重大未知 | 人共同决策；不写实现代码 |

定级纪律：判不准往上取；按本次改动定级；触碰 P1 触发项即 P1；核心定义模糊按核心；升级随时，降级需重新定级并记录；P1 未确认不编码，P2 未确认不合并。

## 4. 发现的冲突与处理

| # | 张力 | 处理 |
|---|---|---|
| 1 | 「上层只能调用下层」vs「依赖倒置」 | 分开调用图与源码依赖图；调用向下，源码依赖向抽象/稳定侧 |
| 2 | 「同层不相认」vs「共享数据服务」 | 数据服务是下沉的基础子层，不是同层兄弟；共享编排上提 L2 |
| 3 | 「模块无状态」vs「连接池/缓存」 | 区分请求级业务状态与基础设施状态；缓存是派生状态，连接池封装且冷热隔离 |
| 4 | 「第二次出现必须归位」vs「避免错误抽象」 | 同一语义/变化原因才抽；形似则记录不抽取理由 |
| 5 | 「P3 简单」vs「P2 跨文件」 | 实质性跨文件/跨模块按 P2；纯机械多文件（重命名/格式化/测试同步）可按 P3 并注明 |
| 6 | 「业务模块必须有价值」vs「ACL/适配器很薄」 | 分业务模块与技术边界模块；后者以隔离/稳定/策略为价值 |
| 7 | 「扇出 ≤8」vs「日志/指标/配置依赖」 | 扇出只数业务契约，排除横切工具与纯值类型 |
| 8 | 「业务重叠没有交隔」 | 按「没有交叠」理解；能力/规则/写入口三重唯一性 |

## 5. 原规格缺口与补充

| 缺口 | 补充 |
|---|---|
| 冷热路径只有目标，没有判据 | 第 5 步：热/冷定义、路径卡、热路径预算、资源隔离、失败/一致性/观测、混合路径拆分 |
| P 级只有一句定义 | 判定顺序、级别表、定级纪律、每级最小产物与人工门、完成定义 |
| 模块没有统一描述格式 | 模块卡：价值、负责/不负责、数据、变化轴、契约、依赖、冷热、验证、删除测试 |
| 契约缺少运行语义 | 契约卡补幂等/顺序/并发/超时/取消/背压/一致性/版本 |

## 6. 自评审结论

**成立的部分**：

- 原始 5 组判据、3 条良好设计、4 个级别均有落点，没有丢条目；
- 每条原则基本都有可执行测试或可检查产物，不是口号复述；
- 冷热路径、P 级门、模块卡、契约卡、路径卡、数据矩阵、验证矩阵构成一套可裁剪的交付物；
- 与 design-before-coding、doc-layout-spec 的分工清楚，冲突时有裁决顺序。

**仍有风险的部分**：

- P3 的「文件边界」与原文「跨文件即 P2」存在解释空间；
- 「整合层」是否就是原文的「整合」，需要确认；
- 扇出排除横切工具是工程上必要的解释，但原文没有明说；
- 复用「第二次出现」加了「同一变化原因」的限定，比原文更保守；
- 冷热只分两类，没有「温路径」，可能不覆盖所有团队的习惯；
- skill 偏长（约 380 行），评审时可再压缩案例与重复表述。

## 7. 待确认问题

1. **分层方向**：是否确认「基础设施 L0 → 领域 L1 → 整合 L2」是自下而上的分层，且「整合」指用例编排/组装层？如果原文的「整合」指外部系统集成层（更靠底层），需要把 L0/L2 的职责重排。
2. **P3 文件边界**：按「实质性跨文件 = P2，纯机械多文件可 P3」，还是严格执行「只要跨文件就 P2」？当前取前者。
3. **扇出计数**：是否同意排除日志/指标/配置等横切工具与纯值类型，只数业务契约？当前取「排除」。
4. **复用规则**：第二次出现时，是「同一语义/变化原因才抽」，还是「只要第二次出现就必须抽」？当前取前者，避免错误抽象。
5. **冷热分类**：是否只保留热/冷两类，混合路径在契约边界拆分？是否需要显式的「温路径」？
6. **P1 人工门形式**：异步评审 + 确认记录是否足够，还是必须同步评审会？当前取「人参与切分/契约阶段 + 最终确认」，形式可异步。
7. **skill 落位**：当前放在项目 `.agents/skills/arch-design-spec/` 供评审；确认后是否移到全局 `~/.dsh/skills/`？
8. **「业务重叠没有交隔」**：是否就是「没有交叠」？如果有别的含义（例如「没有交集隔离」），需要改判据。

## 10. 开发过程规则沉淀（2026-10-21）

用户提供五组开发过程规则（工作方式/验收标准/错误处理/安全边界/工作区卫生），审视后按用户决定沉淀：

- **新建 `dev-execution-spec`**（执行纪律）：五组规则独立成第四个技能，与 design-before-coding（动手前怎么想）、arch-design-spec（架构怎么定）、doc-layout-spec（文档放哪）各管一段；它管「动手到交付怎么干」。开篇即「规则分层：先硬拦截，再自律」。
- **design-before-coding 第 1 步补强**：目标/非目标/至少 3 个验收场景三件套，定义处唯一，执行侧由 dev-execution-spec 引用；第七步末尾增加与 dev-execution-spec 的交接句。
- **常驻上浮**：高危操作确认（发布/删数据/付费/权限/删除覆盖/递归清理/reset --hard/git clean/外发）与密钥禁区写入全局 `~/.dsh/AGENTS.md`——确认类规则不能依赖 skill 按需加载而生效。
- **硬拦截建议**（见新技能第一节表格）：gitleaks、lint no-restricted-syntax、pre-commit diff 输出、审批与受保护分支；commit 纪律与测试有效性难自动化，留 skill 纪律 + CR。
- **未做**：项目内 lint/hook 配置文件未创建，按项目实际技术栈落地时再配；doc-layout-spec 全局副本同步仍待用户决定。
